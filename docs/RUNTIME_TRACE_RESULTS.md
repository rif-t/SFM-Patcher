# Movie Maker runtime trace results

**Status: PARTIAL RUNTIME EVIDENCE.** One-frame Movie Maker PNG output has been produced and inspected. During an image-sequence export, WinDbg hit `ifm.dll+0x2B8060`, `ifm.dll+0x2B75C0`, `ifm.dll+0x2B6610`, and the QImage save callsite at `ifm.dll+0x2B6F0A` in sequence. Their return addresses place each function inside its caller chain; the save call instruction resolves at runtime to `QtGui4!QImage::save`. During a repeat export, the call received basename `a3000000.png`, null format, and quality `-1`; stepping over it returned `EAX=1`, and the user confirmed that image exists. A later export-time write watch confirmed a Material System byte-copy routine writing the MovieDoc CPU buffer, reached through an unnamed `ifm.dll` vtable slot `+0x194` and a `shaderapidx9.dll` stack path. The source resource and GPU operation remain unknown. That repeat image's bytes, dimensions, and pixels have not been independently inspected. WinDbg warns that unwind data is unavailable, so deeper stack frames are uncertain.

## Current runtime buffer observation

- At entry to `FUN_102B6610`, `ESI` was `0x04B2F000`; a read-only dump of `[ESI+0x234]` returned non-null pointer `0xF29D0010`. A second read of the first 32 bytes succeeded and showed repeating `EE FF` bytes. This verifies that the writer's object field contains a readable CPU address at writer entry. The bytes' meaning, readable extent, producer, format, and GPU-readback origin remain **UNKNOWN**; no pixel-format inference is made. These process addresses are ephemeral and not stable identifiers.
- On a subsequent export, `[ESI+0x234]` at `FUN_102B8060` entry still contained `0xF29D0010`, so the same buffer address was present earlier in this frame path. Whether it is reused or rewritten later remains unresolved.
- **Export-time write-watch hit:** a hardware write watch on the first four bytes at that address triggered at `materialsystem.dll` RVA `0x44227`. The preceding instruction at RVA `0x44224` is `mov byte ptr [ecx-2],dl`; at the stop, `ECX=0xF29D0012`, so the store target `[ECX-2]` is the watched buffer start. `dd @ebp+8 L3` showed arguments source `0x0136C480`, destination `0xF29D0010`, count `0x500` (1280). Full loop disassembly showed each iteration reads source offsets `+2`, `+1`, `+0`, writes three sequential destination bytes, then advances source by 4 and destination by 3. This verifies a 4-byte-to-3-byte per-unit CPU copy/conversion into the Movie Maker buffer; channel meaning/format is not inferred.
- The `FUN_102B6610` callsite at RVA `0x2B67BC` is an indirect call through vtable slot `+0x194` on the object in `EDI`; it passes the destination buffer, integer `3`, two local pointers, and a width-derived value. The runtime unwound stack leads from that call through `shaderapidx9.dll+0x1F172` / `+0x13F0A` into the Material System copy routine. This makes an export-time interface-mediated pixel transfer/readback **STRONGLY SUPPORTED**. `!address` classified that routine's source pointer as committed, read/write thread-stack memory, suggesting a stack-resident temporary; its producer, contents, and relationship to any GPU resource remain unknown. Exact interface method, GPU operation, synchronization, and ABI remain **UNKNOWN**. Deeper stack edges carry WinDbg's unwind warning.
- **Forwarded backend dispatch:** on a later export, the call at `ifm.dll+0x2B67BC` executed with `EDX=materialsystem.dll+0x2B670`. That stub loads a function pointer from a Material System interface vtable slot `+0x204` and tail-jumps to `shaderapidx9.dll+0x1F100` (process VA `0x6F4FF100`). WinDbg stopped at the jump instruction before executing it; the following `k` showed the caller as `materialsystem.dll+0x2B682`, returning into `ifm.dll+0x2B7A94`. The dispatch edge from the stub to shaderapidx9 is **VERIFIED**; the deeper route toward the previously observed copy routine remains **STRONGLY SUPPORTED** due to unwind limitations. The target's API name and resource semantics remain **UNKNOWN**.
- **Shader helper entered:** at `shaderapidx9.dll+0x1F16D`, the export-time call instruction targeted `shaderapidx9.dll+0x13E90`. ## Integration-point assessment

| Candidate | Assessment from current evidence |

No candidate is yet runtime-validated as a safe in-process integration point. The simplest viable first prototype remains an offline transformation of an actual exported frame, after the one-frame export and image decoding are verified.
